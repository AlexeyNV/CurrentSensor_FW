# FW 0.4.4-debug — аудит измерительного тракта

## Подтверждённые исходные данные

На FW 0.4.3 при 90-минутной записи получено 54 021 975 отсчётов за
5402,197 с без внутренних пропусков и ошибок SPI/DMA/CRC. Старый
`ACQ_ELAPSED_US=1107230400` равен полной длительности по модулю 2³²;
вычисленная по нему частота 48790 Гц неверна. В отдельных опытах встречалось
`SPI_RX_BYTES=00,85,F3,30`: декодирование `0x85F330 >> 4` как signed 20-bit
даёт **−499917**. Это правильное декодирование полученного слова, но причина
самого слова не установлена. Успешная CRC кадра USB подтверждает доставку
того, что записала STM32, а не корректность аналогового преобразования.

## Аудит SPI1 и DMA

| Путь | Владение и завершение |
| --- | --- |
| `measure`, `regs`, `ina`, `acq probe`, конфигурация профиля | Только foreground при остановленном сборе; `INA229_Transfer` теперь дополнительно отказывает с `INA229_BUSY`, пока SPI принадлежит DMA. |
| Polling acquisition | Foreground выполняет DIAG_ALRT и VSHUNT последовательно. |
| DMA acquisition | TIM3 запускает DIAG_ALRT DMA; завершение RX проверяет TX error, TX NDTR и SPI BSY/TXE, затем снимает CS и при CNVRF=1 запускает VSHUNT. TX/RX буферы статические и изменяются только перед запуском новой транзакции. |
| USB CDC | Не обращается к SPI. Передача и форматирование выполняются вне TIM3/DMA callbacks. |
| Stop | TIM3 останавливается, DMA-запросы отключаются, ожидаются DMA EN=0 и BSY=0, CS поднимается и только после этого возвращается обычный ADC_CONFIG. При неудачной остановке владелец SPI остаётся за DMA и polling-транзакции отвергаются. |

SPI настроен на CPOL=0, CPHA=2-й фронт, MSB first: MOSI считывается INA229
на спаде SCLK, MISO меняется на фронте. Это соответствует
[даташиту INA229, разделам 6.6 и 7.5.1](https://www.ti.com/lit/ds/symlink/ina229.pdf).
Максимум даташита — 10 МГц; минимум CS↓→первый SCLK и последний SCLK→CS↑
составляет 10 нс, межкадровая задержка — 50 нс. Программные операции
между CS и SCLK дают запас по числу тактов MCU, но фактические фронты на
плате следует измерить логическим анализатором. Нормальная полнодуплексная
передача TX/RX не считается ошибкой.

Аудит выявил путь потери диагностической информации: RX IRQ мог обработаться
перед отложенным TX error IRQ, а запуск следующей транзакции очищал флаг TX.
Теперь RX completion проверяет TX error до следующего запуска и перед
снятием CS. Это исправляет порядок обработки ошибки; связь с редким
некорректным кодом тока пока не установлена.

Новые `SPI_OWNER_CONFLICTS`, `DMA_BUFFER_REUSE_ATTEMPTS`,
`DMA_CALLBACK_ORDER_ERRORS`, `CS_STATE_ERRORS` выявляют нарушения владения,
повторное использование ещё занятого буфера, RX completion до окончания TX
и неправильное состояние CS. `SPI_OWNER_CONFLICTS` — счётчик с момента
включения MCU; остальные — счётчики текущей/последней DMA-сессии. Все
счётчики выводятся после остановки в `acq status` и `stream status`.
Они не доказывают отсутствия кратковременного нарушения электрических
таймингов или входного выброса INA229.

## Время и старт

TIM2 остаётся свободно бегущим счётчиком 1 МГц. Его update IRQ увеличивает
старшее 32-битное слово при переполнении. Чтение шкалы повторяется, если IRQ
изменил старшее слово, и учитывает ожидающий UIF, когда прерывания кратко
запрещены. TIM2 IRQ с приоритетом 4 остаётся включённым и после DMA stop;
compare IRQ для ожидания BSY обрабатывается отдельно. 32-битные TIM2
timestamps, `TIME_US`, `SESSION_DURATION_US`, `ACQ_ELAPSED_US` и
`STREAM_ELAPSED_US` в CSF4 v1 сохранены **по модулю 2³²**.

Текстовые `acq status`, `acq test` и `stream status` теперь содержат
`ACQ_ELAPSED_US64`; `stream status` также содержит
`STREAM_ELAPSED_US64`. `RATE_HZ` и `EFFECTIVE_STREAM_RATE_HZ` делят число
отсчётов на 64-битную длительность. Поле частоты в бинарном END также
вычисляется из 64-битного интервала, при прежней длине и расположении полей
CSF4 v1. После примерно 4,97 суток при 10 кГц переполнится отдельный
32-битный счётчик отсчётов; столь длинная сессия остаётся ограничением.

`tools/stream_capture.py` берёт длительности для metadata JSON и расчёта
частоты из текстовых полей `ACQ_ELAPSED_US64` и `STREAM_ELAPSED_US64` после
остановки. Он сверяет младшие 32 бита с бинарным END. Для старых версий FW,
где текстовых полей нет, остаётся источник `CSF4_END_U32`; после rollover
такая длительность неполная. Некорректное или противоречивое US64 отмечается
как ошибка диагностики, исходный END при этом сохраняется в metadata.

При запуске foreground проверяет ADC_CONFIG и один раз читает CNVRF. Чтение
DIAG_ALRT очищает CNVRF согласно даташиту. После этого FW ждёт ещё
`VSHCT_US + 20 мкс`, не читая DIAG_ALRT, и только затем включает TIM3.
Первый учитываемый слот по-прежнему проверяет настоящий CNVRF: нулевой флаг
учитывается как пропуск. Дополнительная подготовка является проверяемой
гипотезой исправления стартового пропуска; нужна проверка на плате.

## Команды отладки

```text
spi config
spi speed 6000000
spi speed 3000000
spi speed 1500000
spi repeat show
spi repeat threshold_ma 50
spi repeat enable 1
spi repeat enable 0
```

PCLK2 читается из RCC; допустимый аппаратный делитель SPI выбирается по
фактической частоте. При штатном PCLK2=96 МГц делители 16/32/64 дают
6/3/1,5 МГц. Переключение допускается только при остановленных acquisition,
USB stream и DMA. Настройка находится только в RAM и после reset вновь
равна 6 МГц. `info`, `spi config`, `acq config` и `stream status` сообщают
фактическую/использованную SPI speed. Неподдерживаемая частота или занятый
SPI дают явный `ERR`.

Повторное чтение выключено по умолчанию и разрешено только в DMA-режиме
BALANCED, PRECISION или LOW_NOISE. Включение в FAST возвращает
`ERR: REPEAT_REQUIRES_DMA_NON_FAST`; попытка позже запустить FAST/polling
с оставленным включённым повтором также отвергается. При превышении
порога по модулю тока, исходный отсчёт записывается как обычно. Для первого
пересечения порога после возврата ниже него запускается дополнительное
чтение VSHUNT через DMA. Хранятся до четырёх событий с исходными и повторными
RX-байтами, RAW, кодами, slot, TIM2 timestamp, промежутком между
транзакциями и статусом. Ошибка повтора не удаляет исходный отсчёт и не
выдаёт недостоверный повтор как измерение. `SUSPECT_SAMPLES` считает все
отсчёты выше порога; `SUSPECT_PER_MILLION` нормирует их на число
действительных отсчётов. Если реальный ток превышает 50 мА, порог следует
увеличить: это диагностический порог для опыта при нулевом токе.
INA229 преобразует асинхронно относительно TIM3, поэтому смену внутреннего
результата между двумя чтениями без отдельной проверки CNVRF установить
нельзя: отчёт честно пишет `NEW_CONVERSION_BETWEEN_READS: POSSIBLE_UNOBSERVED`.
Дополнительный DMA может увеличить задержку и пропуски; режим не является
испытанным исправлением выбросов.

## Порядок аппаратной проверки

Не стирайте сектор 7 с Flash-калибровкой. После прошивки проверьте `info`,
`cal show`, `measure`, `regs`, `spi config`, `acq config`, затем:

1. При отключённой нагрузке выполнить `acq profile set balanced`, `acq mode dma`, `spi speed 6000000`, `stream anomaly set 50`. Снять 5, 30 и 60 с через `python tools/stream_capture.py --port COM7 --profile balanced --acq-mode dma --seconds 60 --output balanced_6mhz.csv` (заменить COM-порт и длительность).
2. Повторить с `spi speed 3000000` и `spi speed 1500000`. После установки скорости закрыть PuTTY до запуска Python; настройка RAM сохраняется до reset MCU.
3. В BALANCED при нулевом токе включить `spi repeat threshold_ma 50`, `spi repeat enable 1`, снять диагностическую запись и после Stop выполнить `spi repeat show`, `stream anomaly`, `stream timing`, `stream status`. Затем `spi repeat enable 0`.
4. Выбрать FAST и наиболее перспективную частоту, снять 5, 30 и 60 с. Проверить `CNVRF_NOT_READY`, `LOST_SAMPLE_SLOTS`, интервал timestamp, SPI/DMA/CRC, частоту. Для rollover записать более 72 минут и сравнить `ACQ_ELAPSED_US64`, `STREAM_ELAPSED_US64`, бинарный END и длительность GUI.

Для сравнения без непрерывной USB-передачи уже доступен `acq test 5`:
выполнить его при тех же профиле и SPI speed до и после streaming.

Для каждого опыта сохранить число отсчётов, подозрительных значений и
событий на миллион, полный `SPI_RX_BYTES`, скорость SPI, время обслуживания,
ошибки SPI/DMA/USB, CRC, пропуски и фактическую частоту. Отсутствие
выбросов в коротком опыте не доказывает их устранения. Если выброс
сохраняется, измерить CS, SCLK, MOSI и MISO логическим анализатором на
самом INA229; проверить 10/50-нс интервалы, форму фронтов, SPI mode,
неожиданные импульсы CS, байтовое выравнивание и сравнить захваченное MISO
с `SPI_RX_BYTES`. Одновременно измерить напряжения на VIN+/VIN− и питание
INA229. Причина редких выбросов пока не подтверждена.

Проверки на ПК: `make -j4`, `cmake -S tests -B build/host-tests`,
`cmake --build build/host-tests --config Debug`,
`ctest --test-dir build/host-tests -C Debug --output-on-failure`,
`python -m unittest discover -s tools -p "test_*.py"`.
