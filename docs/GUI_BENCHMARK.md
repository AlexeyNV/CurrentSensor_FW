# GUI v0.1: измеренные результаты

2026-11-11, Windows 10 19045 x64, Python 3.12.3, NumPy 2.5.4,
PySide6 6.12.0, PyQtGraph 0.14.0, VisPy 0.15.2. Результаты относятся к этому
компьютеру и короткому синтетическому прогону, не к аппаратному USB-тесту.

Исходные отчёты:

## Потоковый GUI с RAW-записью

Штатный Qt event loop, QTimer PreciseTimer 33 ms, четыре режима подряд примерно
по 3 s. DEMO генерирует 10 kHz по времени сессии; recorder пишет CSV/binary/CSF4/JSON.

| Режим | Обновлений графика/с | CPU, % одного логического ядра | RSS, MB |
|---|---:|---:|---:|
| RAW | 25,88 | 171 | 207 |
| MEDIAN3 | 25,98 | 163 | 208 |
| MEDIAN5 | 25,93 | 150 | 211 |
| RAW + MEDIAN3 | 23,36 | 162 | 213 |

Принято и записано **123750 RAW-точек**, 12,3749 s между первым и последним TIM2,
расчётная частота 10000 Hz. CRC, gaps, acquisition loss и recorder loss — 0.
26 диагностических аномалий — заданные синтетические импульсы, они сохранены.
Это проверка программного тракта mock → shared decoder → GUI/recorder,
**не подтверждение 10 kHz с реальной платой**.

Целевые устойчивые 30–60 FPS на обычном Windows-окне пока **не достигнуты**.
Offscreen с PreciseTimer показал около 29–30 обновлений/с, но не заменяет результат
реального окна. Частота измерений не связана с FPS. Интерфейс позволяет работать,
однако запас по плавности при записи и двух кривых требует дальнейшей оптимизации.

## Большие записи и zoom/pan

В каждом случае 30 синхронных обновлений, чередование общего вида, 10% и 1%
интервала, перемещение по истории. Набор содержит шум, ступень, импульсы 1/2/3
отсчёта, отрицательный экстремум и gap. Кеш проверяет сохранение исходных индексов
и амплитуд экстремумов; разрыв исключён из соединяющих линий.

| Точек | PG + кеш, обновлений/с | Builtin peak | VisPy | PG cold index, ms | PG zoom/pan p95, ms | PG RSS, MB |
|---:|---:|---:|---:|---:|---:|---:|
| 100000 | 24,67 | 94,29 | 48,37 | 16,5 | 45,8 | 123 |
| 600000 | 21,30 | 67,53 | 43,24 | 9,4 | 65,9 | 152 |
| 3000000 | 22,68 | 68,60 | 43,25 | 43,3 | 66,8 | 227 |
| 10000000 | 22,99 | 48,16 | 42,29 | 150,9 | 85,7 | 426 |

У PG + кеш среднее время подготовки запроса 0,23–4,45 ms, обновления с paint/readback
39–43 ms. В среднем подготовка включает построение впервые затребованных уровней
кеша; последующие запросы используют кеш. VisPy на 10M: подготовка 4,30 ms,
update/readback 19,31 ms, RSS 544 MB. Полные CPU/max/update-показатели — в JSON.
CPU выше 100% означает суммарную работу нескольких потоков, нормированную на одно
логическое ядро; RSS включает Qt, массивы, кеш и ресурсы графического backend.

**Ограничение сравнения:** production PyQtGraphRenderer содержит оси, сетку,
легенду и обзор с регионом; builtin — один PlotWidget, VisPy — одна GL-кривая.
Для PG вызывается QWidget.grab(), для VisPy canvas.render(), чтобы не измерять
только постановку команды отрисовки. Это пропускная способность paint/readback,
а не измеренный FPS предъявления кадра монитором. Результат не позволяет обещать
двукратное ускорение всего GUI простой заменой renderer.

Builtin peak быстр, но не сохраняет исходные времена экстремумов и может смешивать
смысл gap при повторной агрегации; поэтому он не выбран для измерительного графика.
Собственный кеш хранит first/min/max/last и связи через gaps. VisPy использует те
же данные за интерфейсом renderer; production GUI пока остаётся на PyQtGraph.
GPU-прототип перспективен, но для переключения необходимо реализовать равнозначные
оси/обзор/курсоры/выбор области и повторить сравнение; текущий выигрыш недостаточен
для вывода о необходимости полной переписи приложения.

При профилировании обнаружено, что np.searchsorted копировал поле времени из
структурированного массива при каждом поиске. Двоичный поиск по скалярам устранил
полное копирование 10M значений на каждом zoom/pan. Линейное прореживание исходных
данных не применялось. Кеш обзорного графика также повторно используется для
неизменной истории.

## Фильтры

20 повторов секунды данных каждого rate, блоки до 128 точек, NumPy. Значения —
миллисекунды CPU-тракта подготовки на одну секунду входного сигнала (wall time,
без ожидания реального времени, приёма и диска):

| Отсчётов/с | RAW | MEDIAN3 | MEDIAN5 | RAW + MEDIAN3 |
|---:|---:|---:|---:|---:|
| 1000 | 1,43 | 1,37 | 1,34 | 1,51 |
| 2500 | 3,53 | 3,51 | 3,64 | 3,76 |
| 5000 | 7,16 | 6,53 | 6,55 | 6,61 |
| 10000 | 12,93 | 13,02 | 12,97 | 13,29 |

Production вычисляет оба median один раз при приёме, независимо от выбранного
вида, чтобы переключение не нарушало границы фильтра. Поэтому RAW имеет сравнимые
затраты; это не утверждение, что копирование RAW само по себе требует 13 ms.
Результаты фильтров не записываются вместо RAW.

## Воспроизведение проверки

Команды — в [GUI.md](GUI.md). Не запускать несколько графических benchmark
одновременно: они конкурируют за CPU/GPU. GUI-тесты выполняются без платы,
а итоговый аппаратный тест должен отдельно проверить 5/30/60 s на всех профилях
и целостность записи при активных zoom/Freeze/filter/trigger.
