# FW 0.5.0: расследование RAW-выбросов

Аппаратный и offline-анализ выполнены 14 ноября 2026 года. Итог — **D:
данных недостаточно для локализации источника; нужна физическая трасса SPI**.
Ошибка Python-декодирования/экспорта проверена и не воспроизвелась: исходные
аномальные RAW присутствуют в CRC-корректном CSF4 v2 и совпадают с CSV.
Это ограничивает область поиска, но не доказывает исправность участка
INA229 → SPI → DMA → RAM → формирование CSF4.

Прошивка, SPI 6 МГц, CSF4 v2, GUI, Flash и калибровка не изменялись.
Фильтрация, исправление RAW, reject, CAL SET/SAVE, commit/push не выполнялись.

## Источники и воспроизводимость

Основные источники — четыре этапа `results/hil/accuracy_100ma/`.
Дополнительно проверены 6 старых одиночных HIL streaming-записей FW 0.5.0
и 2 GUI-архива CSF4 v2. Принадлежность FW проверяется по сохранённому INFO
или stream status, не по имени каталога. Копия ZERO_BEFORE из первоначального
HIL-каталога исключена из повторного подсчёта по SHA-256 всего CSV.
Старые сессии остаются отдельными наблюдениями; одинаковая строка версии
не доказывает идентичность сборок и электрических условий.

Новая запись `raw_forensics/ZERO_84_300/` выполнена после ответа оператора
«тока нет». Сохранены RAW CSV, полные принятые бинарные байты в cdc.log,
END, параметры режима и диагностические отчёты. Подтверждение не подменено
измерением внешнего нуля. Всего разобрано **13 уникальных записей,
13 943 807 отсчётов, 60 статистически подозрительных событий**.

Производные результаты:

- [events.csv](../results/hil/raw_forensics/events.csv): события, RAW HEX/bin,
  реальные соседи, XOR/Hamming/позиции битов, ближайшее нормальное значение.
- [summary.json](../results/hil/raw_forensics/summary.json): полный расчёт,
  по 20 предыдущих и последующих RAW для каждого события, timestamps,
  медианы, интервалы, повторяемость, диаграммы по всем 60 событиям.
- В каждом подкаталоге `analysis.json`, `verification.json` для HIL
  и `event_<sequence>.png` с током, unsigned RAW и всеми 24 битами.
  GUI verification включён в analysis.json; исходные GUI CSV не содержат RAW24,
  поэтому RAW восстановлен из их исходного `.csf4`, а каждый CODE/TIM2/slot
  и время сравнены с исходным GUI CSV. Калиброванный ток в этом анализе не используется.

Исходные файлы не переписывались. Дополнительные replay-результаты направлены
в raw_forensics, а не в каталоги исходных испытаний. Кеши воспроизводимы.

```powershell
.\.venv\Scripts\python.exe -m tools.hil.raw_forensics --include-comparison
# Повторный offline-анализ с использованием уже проверенных производных данных:
.\.venv\Scripts\python.exe -m tools.hil.raw_forensics --include-comparison --reuse-derived
```

Кеш повторно используется только при совпадении SHA-256 исходного CSV;
без `--reuse-derived` выполняется полный replay. Команда анализа не открывает COM.
Применён тот же заранее определённый критерий, что в accuracy-suite:
`abs(I-median)>max(10 mA,8*1.4826*MAD)`, либо RFU, либо RAW/CODE/current mismatch.
Сохранённые RAW не изменяются; normal_subset — только описательная статистика.
Ближайший нормальный RAW выбирается по расстоянию signed CODE среди всех
неотмеченных отсчётов этой записи, а не по расстоянию битов. Это не реконструкция
«правильного» слова. Отдельно перечислены одно-битные варианты, встречавшиеся
в других местах той же записи; они никогда не подставляются вместо соседей.

Два из восьми событий отличаются ровно одним битом от следующего **реального**

ни следующий отсчёт этого события не равны FFFED0. Такое слово встречается
в других местах записи. Следовательно, называть этот случай доказанным
одно-битным повреждением соседа нельзя. Для 020810 оба соседа 000010:
различаются **два бита, 17 и 11**, а не один. Остальные исходные события
также имеют многобитные различия с обоими соседями.

## Повторяемость, знак и время

Во всех 13 записях только **5 из 60** событий имеют HD=1 хотя бы с одним
реальным соседним словом; 55 имеют многобитное различие с обоими соседями.
Для 7 событий существует одно-битный нормальный вариант где-либо в записи;
это более слабое наблюдение, оно не является установленным происхождением.
Все 60 событий изолированы — один отсчёт. Физическая длительность импульса
не установлена: один отсчёт нельзя автоматически считать импульсом ровно 84 мкс.

Повторяются точные RAW: 624810 — 6 раз, 020810 — 5, 62C810 / 62C950 /
020950 / B5F6D0 — по 4; 66C950 — 2 раза, включая независимый GUI-архив.
Семейства старшего байта: 62 — 15 событий, 02 — 11, FD — 7, 7F — 7,
B5 — 5, 66 — 3. Наблюдаются устойчивые сложные шаблоны, а не только один
плавающий бит знака. Само повторение не локализует ошибку между прибором,
линией SPI и памятью STM32.

Определение перехода через ноль: знаки CODE в i−1 и i+1 строго противоположны,
оба соседа не отмечены как аномальные; нулевой CODE не считается положительным.
В исходных нулевых записях переход есть в **3/8 событий**, против
**660164/1430259 = 46,16%** обычных подходящих позиций. В новом нулевом
тесте — 11/27 против приблизительно 46,17%. По всем сессиям 27/60 событий.
Преобладание выбросов именно на наблюдаемом переходе через ноль не показано.
Между сохранёнными чтениями возможны внутренние преобразования; соседние
SPI-отсчёты не описывают все внутренние значения ADC.

Временная связь сильнее: у всех 8 исходных событий интервал перед отсчётом
91–102 мкс, после — 65–73 мкс. Описательный диапазон `before>90 && after<75`
содержит **8/8** событий и **187465/1430259 ≈13,11%** обычных позиций.
В новом тесте — 21/27 событий против примерно 13,65%; во всех записях 52/60.
Пороги выбраны после просмотра первоначальных событий: это исследовательская
корреляция, не независимый причинный тест. Timestamp ставит STM32 при
обслуживании завершения транзакции, а не при внутреннем преобразовании
INA229 и не на физическом фронте последнего SCLK. Время выполнения callbacks
может влиять на эту величину. Направление причинности не установлено.

Счётчики service-cycle являются итогами сессии. Индивидуальной привязки
overrun к этим sequence нет; она не выдумывается из общего числа предупреждений.

В нагруженных записях около +117 мА — **0 MAD-событий на 4 288 452 отсчёта**.
Это аргумент в пользу зависимости от режима/уровня входа, но ток был изменён
в другом интервале времени. Он не доказывает причину и не исключает редкое
событие под нагрузкой. Два превышения ±10 мА относительно показаний Fluke
в длинной нагруженной записи — отдельная категория, не RAW-повреждения.

## Новое испытание и ограничение 150 мкс

ZERO_84_300: Native DMA, ADC_CONFIG=AA68, AVG=1 результат (поле AVG=0),
ALATCH=1, SPI verify OFF. **3 573 760 отсчётов**, 11 912,323 Гц по TIM2,
**27 событий**, 0,089998 события/с, 7,555 события/миллион отсчётов.
Обычная составляющая: среднее −0,108699 мА, STD 1,613669 мА;
полный ряд: среднее −0,037195 мА, STD 63,262730 мА,
MIN −32521,1875 мА, MAX +32765,6875 мА. Нулевой шум не описывает хвосты ряда.
Ранее записанные 300 с при 84 мкс: 21 событие, 5,875 на миллион.
Это повторение при одной настройке, а не тест зависимости от частоты.

END получен. Replay/CSV совпадают. CRC/frame/sequence/TIM2 ошибок,
SPI/DMA errors/timeouts, runtime losses и buffer overflows нет.
582 service cycles >=84 мкс, максимум 86 мкс: сохранены как предупреждения.
Преднамеренный STOP tail в END не переименован в runtime loss.

150 мкс штатно доступны как BALANCED ADC_CONFIG=AAA8, но **не для Native
streaming в текущей FW 0.5.0**. Проверено двумя способами:

1. `acq alert adc 150` → `ERR: BAD_COMMAND`.
2. `acq capture native`, `acq profile set balanced`, `acq alert adc profile`,
   `acq native latch 1`, `spi verify off`, `stream start` →
   **`ERR: REPEAT_REQUIRES_DMA_NON_FAST`**.

Последний текст является существующим общим именем статуса
ACQ_DIAGNOSTIC_MODE_UNSUPPORTED; это не доказательство включённого repeat.
В Acq_Start условие Native+stream требует FAST, explicit 84, latch и verify OFF.
Отказ подтверждён кодом и платой, сохранён в profile150_probe.json/log.
Затем восстановлены FAST/84 и capture continuous; calibration before/after
совпали. 150-мкс поток не записывался, его частота/шум/число событий неизвестны.
Требование 10000 отсчётов/с к нему не применялось. FW ради эксперимента не менялась.

## Аудит тракта

В StartTransfer DMA повторно запускается только при отключённых обоих streams,
свободном SPI/BSY и поднятом CS. Команда `(reg<<2)|1`, длина VSHUNT 4 байта,
первый принятый байт исключается. RX completion проверяет TX NDTR/errors,
отключает SPI DMA requests; CompleteOrSettle проверяет TXE/BSY перед CS HIGH.
FinishTransaction составляет RAW из rx[1], rx[2], rx[3] до следующего запуска.
Для Native first_raw и first_rx копируются в pair_current; CommitPrimary
копирует RAW по значению в acquisition ring. Новая транзакция очищает общий
RX только после этой фиксации. DMA/TIM2 имеют приоритет 4, EXTI — 5, USB — 6;
одинаковый приоритет DMA/TIM2 не допускает взаимного вытеснения этих IRQ.
Очевидное преждевременное переиспользование RX этим аудитом не обнаружено;
это проверка кода, не доказательство отсутствия всех гонок или повреждения RAM.
Generation-aware watchdog не менялся.

В StreamCore_BuildStep RAW передаётся как `sample->raw & 0xFFFFFF`, little-endian
uint32. Python берёт те же 24 бита и вычисляет `(raw>>4) - (sign ? 0x100000 : 0)`.
Независимая повторная сверка проверяет каждую тройку sequence/TIM2/RAW по SHA-256,
CODE, исходный ток и rollover-safe elapsed; все HIL/GUI записи прошли.
Это исключает проявившееся несовпадение CSV и сохранённого USB-потока,
но CRC защищает только кадр после его формирования в STM32, не SPI.

По [даташиту TI INA229, §7.3.2 и §7.5.1](https://www.ti.com/lit/ds/symlink/ina229.pdf)
continuous обновляет выходные регистры, чтение не останавливает преобразования,
данные возвращаются в том же SPI frame. Документ допускает чтение в любой момент.
Из этих положений нельзя вывести, что наблюдаемый RAW является «разорванным»
чтением: эту гипотезу требуется проверять, а не объявлять штатным свойством INA229.

## Минимальный захват логическим анализатором

Подключить общий GND и высокоомные входы совместимого 3,3-V анализатора:
PB1 ALERT, PB0 CS, PA5 SCLK, PA7 MOSI, PA6 MISO. Никакой свободный GPIO
автоматически не переназначается. SPI mode 1, MSB first; MOSI выборка на
спаде SCLK, MISO изменяется на фронте. Рекомендуется цифровая запись не ниже
50 MS/s для SCLK=6 МГц; короткие проводники. Декодировать 0x2D (DIAG_ALRT,
3 байта всего) и 0x11 (VSHUNT, 4 байта всего), отдельно каждое CS LOW.
Первый MISO-байт команды не включать в 24-битный результат.

Если анализатор умеет последовательностный trigger, настроить его на VSHUNT
с верхним байтом, отличным от 00/FF при нулевом токе; это только условие
захвата крупных событий, не критерий исправления данных. Сохранять как минимум
несколько предшествующих ALERT и полные транзакции до/после. Если такого trigger
нет, использовать сжатый/потоковый захват переходов с достаточной глубиной и
offline-поиском аномального слова. Короткий произвольный захват не исключает
редкое событие. GPIO-маркер и изменение FW для этой работы не добавлялись.

Одновременно сохранить CSF4 v2 и RAW CSV. Сопоставить последовательность
нескольких RAW вокруг события с логической трассой: sequence в CSF4 не является
номером внутренней конверсии, а аппаратный и TIM2 часы не имеют общего начала.
Проверить ровно 32 такта, команду 0x11, CS HIGH только после окончания,
число ALERT и положение обеих транзакций относительно них.

Если физический MISO и RAW CSV совпадают на аномальном слове, Python/экспорт
и изменение этого слова после приёма исключаются для данного события.
Если на выходе INA слово нормальное, а возле MCU другое — искать электрический
тракт. Если оба физических захвата нормальные, а CSF4 иной — искать STM32
SPI/DMA/RAM/publication; декодер анализатора тоже проверить по отдельным битам.
Если clocks/CS правильные и аномальное слово уже выдаёт INA, это ещё не
доказывает цифровой дефект INA: остаётся проверить аналоговый вход и питание.

## Проверки

Прошли **49 CLI/HIL-тестов и 96 GUI-тестов**. Новые проверки охватывают
XOR/позиции битов, реальные соседи вместо гипотетических, строгий переход
знака, replay с rollover TIM2, сохранность источников и ранние CSV без
калиброванной колонки. Логи тестов находятся в raw_forensics.
