# FW 0.4.4-debug: диагностика остановки CSF4

## Что установлено

Команда остановки в существующем протоколе — `stream stop` с LF. Python
отправлял именно её. Предыдущий вывод `capture failed: Write timeout` не
содержал имени операции. По одному CSV невозможно определить, случился ли
timeout при записи STOP, при проверочном `ping` после END или при запросе
`stream status` / `stream timing` / `stream anomaly`. В старом запуске нет
бинарного END и заключительного metadata JSON, поэтому успешное завершение
сеанса не доказано. Последний RAW-отсчёт и подозрительное значение сохранены
как полученные; файл не менялся.

На STM32 обработчик CDC RX вызывает `App_CdcRx`, кладёт байты в кольцо 256 Б и
сразу повторно включает OUT endpoint. Основной цикл при активном stream
разбирает до 32 байт за проход, включая `stream stop`; затем выполняет
`Acq_Stop()` и запрашивает END. TIM3 и DMA имеют приоритет выше USB, но не
ожидают USB или SPI блокирующим циклом в IRQ. Краткое отключение прерываний в
этом пути используется только при переполнении RX-кольца. Проверка владения
SPI в FW 0.4.4-debug не меняет обработчик CDC RX. Если STOP дошёл до
прошивки, нормальный путь формирует END после опустошения очереди; ожидание
END ограничено также на стороне FW. Код не доказывает, что USB OUT смог
принять команду в сбойном запуске. Нужен новый запуск с диагностикой стадии.

PuTTY не может открыть COM18, пока скрипт держит этот порт: эксклюзивное
владение COM со стороны Windows ожидаемо и само по себе не свидетельствует
о зависании STM32.

## Новая диагностика и завершение

Скрипт обозначает `PORT_OPEN`, `STREAM_START_COMMAND`, `STREAM_ACTIVE`,
`STOP_COMMAND_WRITE`, `WAIT_FOR_END`, `READ_FINAL_DIAGNOSTICS`, `PORT_CLOSE`
и `POSTPROCESS`. При исключении он печатает полную трассировку, команду,
длительность, число сохранённых отсчётов и кадров, CRC/frame/slot errors,
наличие END и факт закрытия порта. Та же сводка сохраняется в
`*_metadata.json` с `session_complete: false`, если metadata ещё не создан.
Исходный CSV остаётся без изменений. Успешный отчёт содержит
`session_complete`, `csv_matches_end`, `incomplete_reason` и `port_closed`.

В момент STOP запись выполняется в отдельном потоке с прежним `write_timeout=1`
с, а чтение CSF4 продолжается. Ожидание END ограничено 5 с после запроса STOP;
поток записи имеет ограниченное ожидание завершения. Повторная отправка STOP
после write timeout автоматически не выполняется: неизвестно, сколько байт
команды принял драйвер COM. При отсутствии END запись явно помечается
`END_MISSING`; она не считается завершённой даже при непрерывном slot_index.
Порт закрывается при выходе из контекстного менеджера, включая исключения.

При попытке короткой проверки COM18 в текущем окружении вызов открытия порта
задержался более чем на 20 с; до `STREAM_START_COMMAND` и создания CSV дело
не дошло. Процесс был остановлен. Отдельный пробный вариант с timeout в
Python-потоке тоже не решил блокировку системного вызова открытия и был
отменён. `write_timeout` относится к записи, а не к открытию COM. Это
наблюдение о доступности COM18 в момент проверки не устанавливает причину
прежнего Write timeout после 60-секундной записи.

## Проверка на плате

Закройте PuTTY перед запуском утилиты. Сначала снимите 1 с, затем 5 с и 60 с:

```powershell
.\.venv\Scripts\python.exe tools\stream_capture.py --port COM18 --profile balanced --acq-mode dma --seconds 1 --output recordings\stop_1s.csv
.\.venv\Scripts\python.exe tools\stream_capture.py --port COM18 --profile balanced --acq-mode dma --seconds 5 --output recordings\stop_5s.csv
.\.venv\Scripts\python.exe tools\stream_capture.py --port COM18 --profile balanced --acq-mode dma --seconds 60 --output recordings\stop_60s.csv
```

Сверьте в JSON `session_complete=true`, `csv_matches_end=true`,
`post_status_matches_end=true`, `crc_errors=0`, `slot_gaps=0`. После закрытия
скрипта откройте PuTTY на COM18 и выполните `ping`, `stream status`, `measure`.
Затем проверьте старт и Stop в GUI. При повторной ошибке сохраните stderr
целиком и partial metadata; ключевые поля — `stage`, `command`, `end_received`
и `port_closed`. Если после timeout устройство продолжает бинарный поток,
вновь откройте COM18 и отправьте обычный `stream stop` с Enter, затем
дождитесь END и `STREAM: TEXT` перед `ping`. Если это не удаётся, проверьте
USB OUT на анализаторе USB и CDC RX в отладчике; причина остаётся аппаратно
неподтверждённой.

GUI v0.1.3.1 использует те же `stream start` / `stream stop` и ожидание END.
Host-side интеграционный тест с ответом `FW: 0.4.4-debug` проходит; реальная
работа GUI с новой прошивкой должна быть проверена на плате.

Проверено на ПК: `make -j4`, 10 C-наборов CTest, 27 Python CLI-тестов и 87
GUI-тестов. Тесты имитируют нормальную остановку 1/5/60 с, активный CSF4,
занятую очередь, задержанный или отсутствующий END, write timeout на STOP,
`ping` и диагностике, USB disconnect, закрытие и повторное открытие COM,
а также равенство числа строк CSV и `USB_SAMPLES_SENT`. Аппаратный повтор
ошибки с новой диагностикой ещё не выполнен.
